自動更新ブログがまた止まった。今度は88日、原因は在庫切れ

執筆： hybs02

実体験ブログ運営自動化Claude Code失敗談

このブログの最後の記事は、8月3日に出たものです。この記事を書いている10月30日の時点で、88日間、新しい記事が1本も出ていませんでした。

以前、自動更新が1ヶ月まるごと止まっていた話 を書きました。その記事は「見える化されていても、見なければ意味がない」で締めて、「月に一度、最終公開日を見る」を自分のルールにした、とも書いています。それでも、今回はその倍以上の期間が空きました。

ただ、今回は前回と中身が違います。何も壊れていませんでした。

壊れていないのに止まっていた

このブログは、書き溜めた記事を「在庫」のフォルダに置いておくと、月曜と木曜の朝7時に1本ずつ自動で公開する作りです（作りの詳しい話は 自動公開を仕組み化して運用した記録 に）。

8月6日から10月29日までの月曜と木曜は、25回ありました。記録を見ると、23回は予定どおり朝7時に動き、9月12日の夜に1回、予定外に動いています。8月13日と9月10日は記録が無く、理由は分かっていません。そして動いた24回は、すべてこう書いて正常に終わっていました。


BACKLOG_EMPTY: scheduled/ に記事がありません。補充が必要です。

在庫が空なので、出すものが無い。前回は起動用のファイルが壊れて処理そのものが走っていませんでしたが、今回は走ったうえで「何もしない」をくり返していました。在庫切れはエラーではなく正常な終わり方として扱う作りにしていたので、エラーの記録も空のままです。

在庫の補充は、もともと人がやる前提にしてあります。6月にこの仕組みを作った時、Claude Code のクラウドの定期実行がつながらず、PC 側で Claude Code を無人で呼ぶ設定もうまくいきませんでした。出来を見ながら書きたかったこともあって、在庫が減ったら Claude Code に「補充して」と頼む形にしました。管理用のパネルにも、在庫が2本以下になると「Claudeに『補充して』と伝えてください」と赤く出るようにしてあります。

ただ、このパネルは開いた時にしか見えません。前回と同じ形で、知らせる仕組みはあっても、見に行かなければ届かない。止まっていたのは機械ではなく、補充する側でした。

補充を「スキル」にした

今回は在庫を足すだけでなく、補充のやり方そのものを Claude Code の「スキル」にしました。スキルは、手順書と道具をひとまとめにして、頼めばその手順で動いてもらう仕組みです。中身はこうです。

手順やること
健康診断最後の公開から何日か、在庫は何本か、本番のサイトが見られるかを最初に確かめる
題材このPCで実際に作ったもの・踏んだ穴から候補を出し、私が選ぶ
取材ファイルに無い数字やその時の事情は、AI が私に聞く
執筆既存の記事の書き方に合わせて書く
機械の検査字数・見出し・リンク切れ・誇大表現・決まり文句を数える
経緯を知らない AI に読ませる書いた経緯を渡さずに、初めて読む人として批評させる
推敲と了承直したうえで私が読み、了承したものだけ在庫に入れる

機械の検査の基準は、公開済みの13本で測ってから決めました。本文の字数は1,429〜2,685字で、真ん中は1,933字でした。もし目安の2,000字を下限にしていたら、13本のうち8本が落ちます。なので下限は1,400字にして、2,000字は目安にとどめました。

健康診断を動かした最初の結果は、「在庫が0本」「最後の公開から88日」でした。

経緯を知らない AI に読ませたら、間違いが次々に出た

いちばん効いたのは、下書きを経緯を知らない AI に読ませる手順でした。中身は同じ Claude ですが、書いた時のやり取りを渡さずに別に立ち上げ、初めて読む人として批評させます（Claude Code ではサブエージェントと呼ばれる仕組みです）。渡すのは、下書きの場所と、狙う読者と、検索してくる時の言葉だけ。こちらの意図や「よく書けたと思う」といった自己評価は渡しません。渡すと、それに沿った答えが返ってきやすいからです。

書いた本人の見直しと機械の検査では、間違いが素通りしていました。今回書いた下書きで、この読み手が実際に見つけた間違いです。

記事見つかった間違い
GPU と音声認識冒頭の「20分の素材に45分」と、本文の表の数字が噛み合っていなかった
勝手にロックされる話Windows の設定値900を「0.9秒」と書いていた。単位は秒で、15分
動画の書き出しの比較「コア12本ぶん使っている」と書いていた。数えていたのは16本ある論理プロセッサ（スレッド）で、この CPU のコアは10本

どれも、機械の検査は通っていました。字数や言い回しは数えられても、数字どうしの矛盾は数えられません。この記事の下書きも同じように読ませていて、「24回きちんと動いた」と書いていたのを、実際の記録と合わないと指摘されて直しています。

もうひとつ、記事に載せるコードを実際にこのPCで動かす、を手順に入れました。これでも2つ見つかっています。GPU のエラーが出るのは、AI のメモでは「モデルを読み込んだ時」でしたが、実際には「最初に書き起こした時」でした。もう1つは .vbs の文字コードの穴で、メモには「エラーになる」とありましたが、実際はエラーも出さずに1行消えるだけでした。どちらも8月に AI と一緒に調べて残したメモで、今日まで正しいと思っていました。

AIに記事を書かせるなら「薄くしない」 で書いたルールに、もう1つ足すなら「測り直す」です。

在庫は3本。それでも、頼まなければまた切れる

この記事を含めて、在庫は3本になりました。月曜と木曜に1本ずつで、このあと、記事を出さなかった3か月にアクセスがむしろ増えていた話と、稼ぐための道具を作ったのに商品がまだ0個の話が順に出ます。

上の表の GPU やロックの話は、下書きまで書いたうえで保留にしました。どれも Claude Code に作ってもらった道具で踏んだ本当の話ですが、ブログの運営にも稼ぐ仕組みにも関わらない、道具の不具合の話だったからです。このブログで書くのは、その2つに関わることだけにします。

止まらない仕組みになったわけではありません。スキルは頼めば最初に在庫を確かめますが、頼まなければ何も確かめません。知らせが届かない、という前回からの穴はそのまま残っています。

もう1つ、書いていて気づいたことがあります。アクセスや費用を出している 運営記録 のページも、7月25日の数字のまま止まっていました。こちらも、更新を頼む人がいなければ止まる作りです。この記事に合わせて、10月30日の数字に更新しました。記事を出していなかった8月から10月も閲覧数は月2,000を超えていて、そのほとんどは機械的なアクセスだと見ています。

このブログについて

当サイトは「AIで自動更新するブログ」を実際に運営しながら、その記録を公開しています。仕組みの全工程は構築の全記録に、アクセスや収益の実数は運営記録にまとめています。
