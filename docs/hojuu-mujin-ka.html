Claude CodeでブログとAI自動化を実際に運用している記録

2026-11-16

記事の補充をClaude Codeの定期実行で無人に。人に聞かない代わりの7つの関門

執筆： hybs02

実体験ブログ運営自動化Claude Code

ブログの記事の補充を、Claude Code の定期実行で無人にしました。毎週水曜と土曜の朝10時に、Claude Code が自分でブログを点検します。公開できる在庫が足りなければ1本書き、7つの関門を通ったものだけを在庫に入れます。

こうしたのは、このブログが8月から 88日止まっていた からです。その時に補充のやり方を Claude Code のスキルにしましたが、スキルは頼んだ時にしか動きません。あの記事の最後の見出しは「在庫は3本。それでも、頼まなければまた切れる」でした。

1回目は11月4日に動き、11月14日までに4回動いています。人に聞かずに在庫まで入れるので、出来の悪い記事がそのまま出ていく心配があります。そこをどう防いでいるかと、4回で実際に何が起きたかを書きます。

何が動いているか

使っているのは、Claude Code のデスクトップアプリにある定期実行です。曜日と時刻を決めておくと、その時刻に新しい作業を自分で始めます。6月にこの仕組みを作った時は、クラウドの定期実行がつながらず、PC 側で Claude Code を無人で呼ぶ設定もうまくいきませんでした。今回はアプリの中の定期実行なので、そのどちらも要りません。追加の費用はかかっていません。Claude Code の有料の契約の中で動き、その契約はほかの作業と共用です（費用の考え方は 個人ブログの運営費を全部公開する に書いています）。

決めたこと中身
曜日と時刻水曜と土曜の朝10時。公開は月曜と木曜なので、その前に在庫を見る
指示書ブログのスキルの「無人で回す」手順に従う。人に質問しない。新しい記事を足すより、サイト全体の質と食い違いを先に見る
守ること書かない題材・同じ事実は同じ数字・公開済みの記事は消さない、など

手順はこの順番です。

順番やること
1健康診断。最後の公開日・在庫の本数・本番のサイトが見られるか
2自動公開のタスクが消えていたら登録し直す
3月の最初の回だけ、運営記録 の数字を更新する
4公開済みと在庫の記事の題と冒頭を全部読む
5在庫の記事を読み直し、古くなった数字や記事どうしの食い違いを直す
6公開済みの記事を1本選んで手入れする。手入れで数字や結論が変わったら、同じ事実を書いているほかの記事もそろえる
7公開できる在庫が4本未満なら、1本書いて足す
8変更を GitHub に上げて公開の仕組みに渡し、報告を残す

2番目は、7月に 1ヶ月止まっていた 時、定期実行の登録そのものが消えていた穴を塞ぐためのものです。新しい記事を書くのは7番目で、先に全体を読ませています。新しい記事が前の記事と食い違ったり、同じ話をくり返したりしないようにするためです。

人に聞かない代わりの関門

6月に 自動公開を作った 時は、公開してよいかの判断（推敲して、公開してよい印を付ける所）は私が持っていました。88日止まった後に決めた補充の手順も、最後は「私が読み、了承したものだけ在庫に入れる」でした。定期実行の回では、その判断を人の手から外しています。代わりに置いたのが、在庫に入れる前の7つの関門です。1つでも通らなければ、その記事は下書きに残して、在庫には入れません。

関門中身
機械の検査字数・リンク切れ・誇大表現・決まり文句などの ERROR が0
経緯を知らない AI の判定下書きを初めて読む読み手が「このまま出せる」か「直せば出せる」と判定した
必須の直しその読み手が「必須」とした指摘を全部直した。事実の指摘は元のファイルで確かめてから直す
2回目の読み必須が3件以上あった時は、直した版をもう一度読ませて、必須が0
動かして確かめる記事に載せたコマンドやコードは、このPCで実際に動かした
越えない線書いてはいけない話に触れていない
食い違わない公開済み・在庫の記事と、数字や結論が食い違っていない

題材の選び方にも決まりを足しました。人に聞かないと書けない題材は選ばせません。その時の気持ちや判断の理由は、ファイルには残っていないからです。ファイルと記録で確かめられる数字だけで書ける題材にして、確かめられない所を残した記事は在庫に入れない。書ける題材が無い回は、書かずに「題材切れ」と報告させます。ブログの運営や稼ぐ仕組みに関係しない記事で埋めるより、在庫が減るほうを選ぶ決まりです。

記事の中の約束も拾わせます。ツールサイトの記事 で、公開から2週間の11月15日ごろに残すか捨てるかを決めると書きました。その日を過ぎた最初の回は、判定に使う数字を最優先の題材の候補にします。

4回で起きたこと

11月14日までの4回を、報告と変更の記録から拾うとこうです。

回公開済みの手入れ補充
11月4日6月の副業の記事を11月の実数に合わせたツールサイトの記事を書いて在庫へ
11月7日Claude Codeとは？ を手入れChrome 拡張の記事を書いて在庫へ
11月11日6月の記事を1本手入れし、同じ事実を書いていたもう1本もそろえた1本書いたが、2回目の読みで必須の指摘が残り、下書きに置いた
11月14日6月の記事を1本手入れし、在庫に入れた記事と食い違う1本もそろえた11日の下書きの指摘を直し、関門を最後まで通して在庫へ

11月11日の回は、関門が働いた回です。1回目の読みで必須の指摘が3件以上あり、直した版をもう一度読ませても必須が残りました。その回は在庫に入れず、次の回で残りを直してから入れています。

1回目の11月4日の回は、記録の上では10時10分に始まり、10時23分に終わっていました。中身はこうです。

やったこと中身
在庫の点検在庫の2本を読み直した。事実は今と合っていて、直していない
公開済みの手入れ6月の AIで副業を自動化する現実的な方法 を、11月時点の実数に合わせた（収益0円・出品0個・小さな道具を11月1日に公開）。見直しの時期を、ほかの記事とそろえて12月にした
補充ツールサイトを作ったその日に公開した話 を書いた。経緯を知らない読み手の判定は「直せば出せる」で、必須の指摘2件を直して在庫に入れた
在庫の本数2本から3本へ

手入れした6月の記事は、11月の実数に照らすと古いままでした。古い記事は書いた日の事実のまま止まるので、新しい記事と並べると食い違います。補充のたびに1本ずつ直す決まりにしたので、古い記事も少しずつ今に追いつきます。

残っている穴

穴は3つあります。

1つ目は、私のPCが起きていて、アプリが開いている時しか動かないことです。PC がスリープ中か、アプリを閉じていれば、その時刻には動きません。公式のドキュメント では、次に起動か復帰した時に、直近7日で逃した回のうち最新の1回だけをやり直します。水曜の朝の回が水曜の夜に動く、ということは起こります。逃した回が2回あれば、1回分は戻りません。

2つ目は、在庫の数が増えないことです。出るのは週2本、足すのも多くて週2本なので、うまく回っても在庫は横ばいです。1回飛ぶか「題材切れ」になるたびに1本ずつ減ります。

3つ目は、出る前に私が読まなくなったことです。関門が見落とすものは、そのまま月曜か木曜に出ます。在庫に入ってから出るまでは、早くて1週間、長いと2週間近くあります。毎回の報告を読めば、出る前に止めることもできます。止める時は、在庫のファイルから「推敲済み」の印（reviewed: true）を外せば、自動公開に乗りません。ただ、関門が見落とした記事を止められるのは、私が報告を開いた時だけです。

このブログについて

当サイトは「AIで自動更新するブログ」を実際に運営しながら、その記録を公開しています。仕組みの全工程は構築の全記録に、アクセスや収益の実数は運営記録にまとめています。
